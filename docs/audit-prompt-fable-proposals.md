# Предложения Fable к системному промпту аудита

Статус: **не применены**. Это список для поштучного принятия/отклонения.
Fable работал под жёстким ограничением: только добавления, ничего не удалять,
не переставлять и не переписывать. Исходный промпт
(`docs/hallugraph-error-audit-system-prompt.md`) не изменён.

Ниже — сводка. Полные формулировки для вставки см. в разборе каждого пункта.

| № | Предложение | Тип | Куда |
|---|---|---|---|
| 1 | `QUERY_ONLY_GROUNDING` — заземление только графом Query | пункт + тег | Слой 3 + теги Слоя 8 |
| 2 | `KGGEN_CONTEXT_FABRICATION`, `KGGEN_RESPONSE_NORMALIZATION` | теги | теги Слоя 8 |
| 3 | `SPARSE_GRAPH_INSTABILITY` — квантование балла на малом графе | тег | теги Слоя 8 |
| 4 | `LITERAL_VALUE_OVERMATCH` — «2011» ≈ «2012» при мягком сравнении | тег | теги Слоя 8 |
| 5 | `flags_vs_gold_spans` — попадают ли флаги в размеченные интервалы | пункт + поле JSON | Слой 6 + §12 |
| 6 | Конвенции полярности `gold_label`/`auditor_label`, значения `stage` | уточнение | §12 |
| 7 | Шкала `kggen_contribution` + сверка с `ORACLE_GRAPH` | уточнение | §12 |
| 8 | `atomic_claims_total` / `_problematic` / `max_claim_severity` | поля JSON | §12 |
| 9 | `missing_signals` — короткие англ. номинальные фразы | уточнение | Слой 8 |

## Что Fable намеренно не трогал

1. Порядок слоёв и правило «сначала HalluGraph, потом GraphEval» — осознанная
   защита от анкоринга.
2. Ровно четыре контрфактика в Слое 7 — `ORACLE_AGGREGATION` уже включает
   калибровку порога; разделение сломало бы фиксированные ключи JSON.
3. Отсутствие рубрики для `confidence` — любая шкала-якорь произвольна и создаёт
   ложную точность.
4. Набор статусов атомарных утверждений в Слое 1 — `UNCERTAIN` + серьёзность уже
   покрывают предложенные `PARTIALLY_ENTAILED` / `EXTRAPOLATED`.
5. Список крупных классов первопричин — должен оставаться стабильным между
   партиями аудитов; хватает детального тега + `NEW_CATEGORY`.

## Замечание к пунктам 6–8

Пункты 6, 7 и 8 меняют схему сводного JSON (§12). Их надо принять или отклонить
**до** пилота: если принять после, ранние аудиты будут в старой схеме, и
агрегация получит разнородные записи. Пункты 1–4 (только новые теги) и 9
безопасно добавлять в любой момент — они расширяют словарь, а не структуру.
