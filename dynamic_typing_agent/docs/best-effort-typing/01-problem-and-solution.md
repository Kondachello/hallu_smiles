# 01. Проблема и решение

## Проблема

Типизация идёт по сущностям (`entity-by-entity`). Для каждой сущности LLM предлагает один или
несколько типов-гипотез, а локальная NLI-модель (HHEM-2.1) проверяет, следует ли гипотеза из
исходного текста (`entailed` / `neutral` / `contradicted`).

В версии `v3` логика была такой: если ни один семантический (не-корневой) тип не был подтверждён
NLI в рамках бюджета попыток, сущности присваивался **структурный корень** `T-ENTITY` с меткой
`entity`.

Поскольку в иерархии типов родителем первого уровня всегда является `entity`, откат «к родителю»
на практике означал откат к `entity`. Итог: как только NLI капризничал (а на реальных данных это
часто), сущность получала **бесполезный служебный тип** `entity` вместо чего-то информативного вроде
`commercial bank` или `financial institution`.

### Формулировка задачи (от постановщика)

> Существует проблема: если NLI не подтверждает тип, присваивается родительский. Но так как на первом
> уровне родительский тип — это `entity`, сущности часто получают «служебный» неинформативный тип.
> Надо сделать зацикливание: если NLI говорит «так себе идея», предложить ещё раз. И, допустим, после
> достижения лимита (например, 3 гипотезы по умолчанию) брать родительский, **а если родительский
> `entity` — брать самый вероятный по мнению NLI**.

## Решение: алгоритм `v4-best-effort`

Идентификатор версии в коде: `ALGORITHM_VERSION = "entity-by-entity-nli-v4-best-effort"`.

### Пошагово (на одну сущность)

1. **Цикл попыток** `attempt = 1 … max_entity_attempts` (дефолт **3**, было 2):
   - LLM предлагает тип(ы)-гипотезы;
   - каждый семантический (не-`T-ENTITY`) тип проверяется через NLI;
   - **каждый** проверенный кандидат складывается в `best_effort_pool` (метка, вердикт,
     `evidence_level`, определение, номер попытки) — даже если он не принят.

2. **Условия остановки цикла** (в порядке проверки):
   - найден **entailed**-тип на этой попытке → `break` (успех, стоп сразу);
   - на этой попытке нет семантических целей → `break` (нечего типизировать);
   - есть **neutral**-кандидаты и `retry_on_neutral = false` → `break` (принять как есть);
   - достигнут `max_entity_attempts` → `break`;
   - иначе — **переспрос**: формируется уточнённая инструкция модели («предложи ДРУГУЮ, более узкую
     переиспользуемую категорию, подтверждаемую спанами доказательств; не повторяй neutral/contradicted
     и не называй саму сущность») и следующая итерация.

   > `retry_on_neutral` (дефолт `true`) — именно то самое «зацикливание при слабом NLI»: чисто
   > нейтральная попытка не принимается сразу, а провоцирует ещё одну гипотезу в поисках entailed.

3. **Финальный выбор типа:**
   - если есть хотя бы один NLI-подтверждённый семантический тип (`semantic_ids`) → используем его(их);
   - **иначе, если `best_effort_pool` непуст** → вместо корня берём **самый правдоподобный** кандидат:
     сортировка по `(_VERDICT_RANK, _EVIDENCE_RANK)` по убыванию, где
     - `_VERDICT_RANK = {entailed: 3, neutral: 2, contradicted: 1}`
     - `_EVIDENCE_RANK = {SOURCE_ENTAILED: 3, DEFINITION_ONLY: 2, UNKNOWN: 1}`

     при равенстве сохраняется самый ранний (более специфичный) кандидат;
   - **корень `entity` остаётся только если `best_effort_pool` пуст** — т.е. модель не предложила
     вообще ничего.

4. **Аудируемость best-effort выбора:**
   - выбранному типу проставляется `evidence_level = UNKNOWN` (через `model_copy`), чтобы явно
     отметить низкую уверенность;
   - записывается человекочитаемая причина `reason` («Best-effort type '…' kept after N attempt(s);
     highest NLI verdict was '…' with no source-entailed type. Chosen over the structural root 'entity'.»);
   - в трейс добавляется событие `type_best_effort_fallback` со всем ранжированным списком кандидатов
     (`ranked_candidates`) — можно посмотреть, из чего выбирали и почему.

### Что осталось прежним

- Корневой тип `T-ENTITY` по-прежнему существует в реестре как корень иерархии (он присутствует в
  списке типов каждого реестра — это **не** ошибка и не откат).
- Правило приёма: тип принимается, если он корневой ИЛИ вердикт NLI ≠ `contradicted`.
- Contradicted-типы теперь тоже попадают в `best_effort_pool`, поэтому в вырожденном случае «все
  кандидаты contradicted» сущность всё равно получит информативный тип (с `evidence_level=unknown`),
  а не `entity`. Это осознанный выбор постановщика в пользу информативности; низкая уверенность
  фиксируется в аудите.
